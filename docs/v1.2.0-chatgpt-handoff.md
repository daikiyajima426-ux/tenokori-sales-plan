## 2. v1.2.0の目的

v1.1.0までの販売計画シミュレーターを、カード型の構造に変更する。

目的は以下。

- 取れた量を複数カードとして登録できる
- 売る形を複数カードとして登録できる
- 販売計画を複数カードとして登録できる
- 販売計画カードが、取れた量カードと売る形カードをつなぐ
- 全体合算で、目標手残りに届くか見る
- カード別に使用量、売上、費用未反映の見込み額を見る
- 取れた量を超える販売計画があれば警告を出す

## 5. 現在の計算ロジック

### 売る形1単位あたりkg

```ts
productUnitKg(product)
```

- `quantityUnit === "g"` の場合：`quantityPerUnit / 1000`
- `quantityUnit === "kg"` の場合：`quantityPerUnit`
- 未入力、不正値、0以下は `0`

### 販売計画カード単位の計算

```ts
calculateSalesPlan(card, harvest, product)
```

計算するもの：

- `unitKg`
- `usedKg = unitKg * plannedUnits`
- `salesYen = pricePerUnit * plannedUnits`
- `takeHomeYen = salesYen`
- `missing`
- `isValid`
- `canCheckStock`

現状の重要点：

- `isValid` は売上集計に使う
- `canCheckStock` は在庫警告に使う
- 両者を混ぜない

```ts
isValid: missing.length === 0
canCheckStock: Boolean(harvest && product && unitKg > 0 && plannedUnits > 0)
```

### 全体集計

```ts
calculateSummary(plan, harvestCards, productCards, salesPlanCards)
```

現在の集計方針：

- `validResults`：売上・手残り・達成率用
- `stockCheckResults`：在庫使用量・在庫警告用

```ts
const validResults = salesResults.filter((row) => row.isValid);
const stockCheckResults = salesResults.filter((row) => row.canCheckStock);
```

売上側：

```ts
totalSalesYen = validResults.reduce(...)
totalTakeHomeYen = validResults.reduce(...)
```

在庫側：

```ts
totalUsedKg = stockCheckResults.reduce(...)
totalOverKg = Math.max(0, totalUsedKg - totalHarvestKg)
```

カード別在庫使用：

```ts
harvestUsage = harvestCards.map((harvest) => {
  usedKg = stockCheckResults
    .filter((row) => row.card.harvestId === harvest.id)
    .reduce(...)
  overKg = Math.max(0, usedKg - harvest.amount)
})
```

警告・注意：

- 総量超過警告
- 取れた量カード別超過警告
- 目標未達警告
- 仮説不足
- データ注意

例：

```text
販売予定量の合計が、取れた量の合計を15kg上回っています。売る量を減らすか、取れた量を見直してください。
通常品の販売予定量が、取れた量を30kg上回っています。売る量を減らすか、取れた量を見直してください。
```

## 7. サンプルデータの現状

基本サンプル：

取れた量：

```text
通常品 150kg
規格外 25kg
加工向け 15kg
```

売る形：

```text
直売所用：1袋 350g
飲食店用：1箱 2kg
規格外まとめ売り：1kg
```

販売計画：

```text
直売所で袋売り：350g × 180袋 = 63kg
飲食店向け箱売り：2kg × 35箱 = 70kg
規格外まとめ売り：1kg × 20kg = 20kg
```

合計：

```text
使用量 153kg
取れた量合計 190kg
未使用量 37kg
```

このサンプルは在庫超過していない。したがって `大きな注意はありません。` は在庫面では正常。

ただし、手残りが少なすぎるという指摘があった。

現在の売上：

```text
直売所：1,800円 × 180袋 = 324,000円
飲食店：11,000円 × 35箱 = 385,000円
規格外：900円 × 20kg = 18,000円
合計 727,000円
```

目標手残り：

```text
800,000円
```

不足：

```text
73,000円
```

ユーザー指摘：

- 140kg使って165,000円は、販売計画サンプルとして弱すぎる
- サンプルの数字が現実感を欠くと、警告ロジックや構造が壊れているように見える
- ただし、変なデータも実際には入力され得るので、サンプルを直すだけでは本質的ではない
- まずロジック・構造側が頑健であるべき

現在の対応：

- ロジック構造を先に改善済み
- 基本サンプルを自然寄りに調整済み
- 警告サンプルを別途追加済み

## 11. 現在の未解決論点

### 1. サンプルデータの現実感

現在のサンプルは在庫面では正常だが、売上・手残りが弱すぎる。

検討案：

- 目標手残りを下げる
- サンプルの価格を上げる
- サンプルの販売数を増やす
- ただし在庫超過サンプルにするか、正常サンプルにするかを決める必要がある

論点：

- サンプルは「成功例」にするか
- サンプルは「警告が見える例」にするか
- 両方を用意するか

### 2. 手残り計算の扱い

現在v1.2.0では、カード別コストを持たないため、

```ts
takeHomeYen = salesYen
```

としている。

READMEにも制約として記載済み：

```text
手残りは現時点では売上見込みとして扱います。
カード別コストはありません。
```

論点：

- v1.2.0のままこの制約で進めるか
- v1.3以降でカード別コストを戻すか
- ただし今回は全面改修は避ける方針だった

### 3. 在庫警告の粒度

現在は以下の2種類。

- 総量超過警告
- 取れた量カード別超過警告

論点：

- 両方必要か
- カード別だけで十分か
- 総量警告は「加工向けなど未使用カード」があると分かりにくい可能性がある

例：

```text
通常品だけ見ると30kg超過
全体では加工向け15kgが余っている
総量では15kg超過
```

この場合、総量警告とカード別警告の両方が出る。

これは情報としては正しいが、ユーザーには少し複雑に見える可能性がある。
